# Profile Webpage Skill

Turns a resume that was already generated by `resume-builder-skill` (a `.docx` in the
`output/` folder) into a single, self-contained **developer-themed webpage** and serves it
on **localhost** so the user can view it in a browser on their desktop.

> **Privacy:** this skill file intentionally contains **no personal data**. The candidate's
> identity, contact details, and all other credentials live **only** in the resume `.docx`
> under `output/` (which is not tracked in git). Read them from that file at runtime — never
> hardcode them here. The generated webpage is also written under `output/` and is therefore
> untracked.

## Inputs

1. **Resume file name** — supplied by the user (e.g. `DevOps Engineer`, `Software Engineer`,
   `<CandidateName>CV-DevOps Engineer`). **This input is mandatory.** If the skill is invoked
   without a resume file name, **stop and explicitly ask the user for it, and do not perform
   any other step (do not read any file, do not install anything, do not generate or serve a
   page) until the user provides it.** Never assume, reuse a name from earlier in the
   conversation, or guess.

   Once provided, match it to a file in the **`output/` folder**:
   - Match **case-insensitively**.
   - The `.docx` extension is **optional**.
   - The `<CandidateName>CV-` prefix is **optional** — accept either the full file name
     (`<CandidateName>CV-DevOps Engineer.docx`) or just the job-description portion
     (`DevOps Engineer`), matching against the part after `CV-`.
   - If exactly one file matches, use it. If **no** file matches, **list the available
     files in `output/` and ask the user to pick one** — do not proceed with a guess. If
     **multiple** files match, list the candidates and ask which one.

2. **Source resume** — the matched `.docx` in `output/` is the single source of truth for
   all content on the webpage.

## Interaction model (always ask first, plan, then confirm)

This skill is used by a person who is **new to webpage creation**, so it runs
**interactively** — never silently:

- **Always take the resume file name from the user.** Even if a name appears earlier in the
  conversation, confirm the resume to use at the start of the run. Never assume or default it.
- **Ask as many clarifying questions as needed before building** — cover at least the visual
  theme variant/accent, layout style, any developer decorations, the localhost port, and
  whether to auto-open the browser. Prefer a small number of concrete multiple-choice
  questions (with sensible recommended defaults) over open-ended ones, and keep asking until
  the design is unambiguous.
- **Present a short written plan and wait for explicit confirmation before execution.** The
  plan should state the matched resume file, the output HTML path, the chosen design choices,
  and the serving command/URL. **Do not read/convert content into a page, write any file,
  install anything, or start the server until the user approves the plan.** (Resolving the
  file name and a read-only content extraction to inform the questions/plan are fine.)

## Output

- A single self-contained HTML file written to the **`output/` folder**:
  `output/<resume-stem>.html`, where `<resume-stem>` is the matched file's name without
  its `.docx` extension (e.g. `output/<CandidateName>CV-DevOps Engineer.html`). It sits alongside
  the source `.docx` in the same `output/` folder.
- All CSS is **inlined** in a `<style>` block — no external fonts, CDNs, or network calls,
  so the page renders identically offline.
- **Create the `output/` folder only if it does not already exist** before writing.
- The page is then **served on localhost** (see Generation steps) and the user is given the
  URL to open.

## Hard rules (read before generating)

- **Truthful and verifiable.** Every word on the webpage must come from the source `.docx`.
  You may **re-format, reorder, and lay out** the content for the web, but you must **never
  invent or embellish** — no new employers, dates, titles, skills, metrics, tools, links,
  or social profiles that are not in the resume. Do **not** fabricate a GitHub/LinkedIn URL,
  a tagline, or a project just because a "developer profile" page usually has one.
- **Preserve sentiment & tone.** Keep the measured, understated voice of the resume
  ("Good understanding of…", "Experienced in…"). Do not add hype, superlatives, emoji, or
  marketing language that is absent from the source. The "developer theme" is **visual
  only** — it must not change the wording's sentiment.
- **One page, clear and concise.** Mirror the one-page nature of the resume: the webpage
  should read as a single, concise profile. Don't pad with filler sections. Include a print
  stylesheet (`@media print`) so it prints to roughly one page on white.
- **Identity & contact details verbatim** as they appear in the resume (name, phone, email,
  work-permit line, address). Read them at runtime; do not paraphrase.
- **Self-contained & local only.** Inline everything; never link the page to external
  resources or upload it anywhere. It is served on the user's own machine only.

## Source of content (read at runtime — nothing is hardcoded here)

Extract everything from the matched `.docx` using `python-docx`. The resume produced by
`resume-builder-skill` has this structure — map each part to the webpage:

- **Header / contact** — candidate name, phone, email, work-permit line, address.
- **Personal summary** — the summary paragraph → the page's intro / "about" block.
- **Professional experience** — each employer, title, location, date range, and bullets.
- **Key competencies** — the listed competencies → a "skills" / tag list.
- **Academic qualifications & certification** — degrees and certifications.

Read paragraph text **and** detect structure (section headers vs. job titles vs. bullets)
from the docx — e.g. shaded/bold uppercase paragraphs are section headers, the muted-blue
runs are job-title sub-headings. If a section is absent in the resume, omit it from the page
(do not invent it).

## Design approach (developer theme)

Aim for a clean, modern **developer / IDE / terminal** aesthetic — visual styling only, no
wording changes:

- **Dark background** (black or near-black, e.g. `#0d1117` / `#000000`) with light text.
- A **monospace** font stack for code-like accents (e.g.
  `'JetBrains Mono', 'Fira Code', 'SF Mono', Consolas, monospace`) and a clean sans stack for
  body prose so it stays readable; rely only on system/web-safe fonts (no CDN).
- **Syntax-highlight-style accent colors** for structure: e.g. a green/cyan for section
  headings, a muted blue (`~#4F81BD`, echoing the resume's job-title color) for job titles,
  a soft amber/teal for the skill tags. Keep contrast high (WCAG-friendly).
- Optional tasteful dev touches that **do not invent content**: a terminal-style header bar,
  a `~/profile —zsh` window chrome, a monospace `$` prompt before the name, line-number
  gutters, or section headers rendered like comments (`// experience`) or tags
  (`<experience>`). These are decoration around the **real** resume text only.
- **Skills/competencies as tag chips**; **experience as a vertical timeline or cards**;
  contact details as an icon-free, copy-friendly list (use unicode glyphs, not external icon
  fonts).
- **Responsive & single-column** so it reads well full-screen and prints cleanly. Include
  `@media print { background:#fff; color:#000; ... }` so a printed copy is legible and ~one
  page.

## Generation steps

0. **Confirm the resume file name with the user.** Always take it from the user for this run
   (do not reuse/guess). If it was not provided, ask for it and stop until they answer.
1. **Resolve the input file** in `output/` (case-insensitive; `.docx` and the
   `<CandidateName>CV-` prefix optional). On no/multiple matches, list `output/` and ask.
1a. **Ask clarifying design questions, then present a plan and wait for confirmation**
    (see "Interaction model"). Do not proceed to steps 2–6 until the user approves the plan.
2. **Ensure `python-docx` is available** (used to read the `.docx`):
   - Check: `python -c "import docx"`
   - If missing, install: `python -m pip install python-docx`
3. **Read the `.docx`** and extract the content and structure (see "Source of content").
4. **Build the webpage**: generate a single self-contained `output/<resume-stem>.html`
   with inlined CSS implementing the developer theme. Every piece of text must come from the
   docx; preserve order and sentiment. Create the `output/` folder only if it does not
   already exist.
5. **Verify the content** before serving: re-read the resume text and confirm every section,
   bullet, skill, date, and contact detail on the page matches the docx exactly, with nothing
   added. Flag to the user anything that could not be represented faithfully.
6. **Serve on localhost.** Start a local static server rooted at `output/` and give the
   user the URL. On Windows/PowerShell, run it in the **background** so it keeps serving:
   - `python -m http.server 8000 --directory "output"`
   - The page is then at `http://localhost:8000/<resume-stem>.html`
   (If port 8000 is busy, pick another free port and tell the user.) Optionally open it with
   `Start-Process "http://localhost:8000/<resume-stem>.html"`.
7. **Report** to the user: which resume file was used, the path of the generated HTML, the
   localhost URL, and how to stop the server (e.g. close the background task / `Ctrl+C`).

## Reference: read a resume `.docx` with python-docx

```python
from docx import Document
from docx.shared import RGBColor

doc = Document(path)
for p in doc.paragraphs:
    text = p.text.strip()
    if not text:
        continue
    # Section-header bar: shaded paragraph (w:shd) or bold uppercase
    pPr = p._p.pPr
    shaded = pPr is not None and pPr.find(
        '{http://schemas.openxmlformats.org/wordprocessingml/2006/main}shd') is not None
    is_header = shaded or (text.isupper() and any(r.bold for r in p.runs))
    # Job-title sub-heading: muted-blue runs (~#4F81BD)
    is_job_title = any(
        r.font.color and r.font.color.rgb == RGBColor(0x4F, 0x81, 0xBD) for r in p.runs)
    style = p.style.name  # e.g. 'List Bullet' for bullet points
```

Tables (e.g. the two-column contact block) are read via `doc.tables`; iterate
`table.rows[i].cells[j].text`. Keep the HTML self-contained: inline all CSS, use unicode
glyphs instead of icon fonts, and add a `@media print` rule for a clean one-page printout.
